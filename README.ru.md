# jiraleaks

English version: [README.md](README.md)

**Поиск утёкших секретов, API-ключей и учётных данных в задачах, комментариях и вложениях Jira.**

`jiraleaks` — консольная утилита на Rust (один бинарник), которая сканирует Jira на
утёкшие секреты. Работает с Jira **только на чтение**, пишет отчёты в шести форматах,
ведёт хранилище находок для сверки между сканами и умеет отправлять алерты в Slack,
Teams или произвольный вебхук.

Сырые значения секретов **не попадают** ни в отчёт, ни в хранилище находок, ни в лог,
ни в алерт: в каждом месте только маскированный превью, хеш SHA-256 и сниппет, в котором
замаскированы сам секрет и соседние секреты того же окна.

- Только чтение: задачи забираются через REST API Jira, состояние Jira не меняется.
- Безопасно по умолчанию: находка несёт маскированный секрет и хеш, но не сырое значение.
  Сниппеты маскируются, спаны логов маскируются, токен Jira и URL вебхуков не печатаются.
- Разворачивается где угодно: релизный бинарник, минимальный Docker-образ, CronJob в
  Kubernetes или таймер systemd.

## Возможности

- **20 встроенных детекторов** — облачные провайдеры, платформы разработки, SaaS и
  мессенджеры, базы данных и строки подключения, форматы ключей и токенов.
- **Детектор пар «логин-пароль»** — пары `user:password` в URL, в JSON-объектах и по
  близости ключей.
- **Свои правила в YAML** — fancy-regex, энтропия, требования к классам символов,
  контекстные слова, denylist; пользовательское правило перекрывает встроенное по
  `rule_id`.
- **Полное покрытие комментариев** — вычитываются и сканируются все страницы ветки
  комментариев, а не только та, что встроена в тело задачи.
- **Сканирование текстовых вложений** (по флагу `--scan-attachments`) — тело вложения
  скачивается потоком с ограничением размера и сканируется тем же движком правил.
- **Allowlist** по значению, SHA-256, регулярному выражению, `rule_id`, ключу задачи,
  ключу проекта и пути поля; загрузка строгая — непригодная запись считается ошибкой
  конфигурации, а не молча игнорируется.
- **Подавление ложных срабатываний**: пороги энтропии Шеннона, общий словарь заглушек,
  требования к классам символов, контекстные слова, лимит находок на задачу.
- **Шесть форматов отчётов**: JSON, NDJSON, CSV, SARIF 2.1.0, DefectDojo Generic Findings
  Import и человекочитаемая сводка.
- **Хранилище находок** (SQLite или PostgreSQL) со сверкой статусов между сканами:
  New / Recurring / Closed / Confirmed / FalsePositive / Resolved.
- **Алерты** в Slack, Microsoft Teams или произвольный вебхук (fire-and-forget, итог
  доставки логируется).
- **Jira Cloud и Server / Data Center** через REST API v2; аутентификация `bearer`,
  `basic` или `none`.
- **Потоковый конкурентный скан** с ограниченным backpressure и интерактивным прогресс-баром.
- **Враждебный ввод ограничен по стоимости**: текст из Jira считается недоверенным, у
  каждого цикла на сегмент есть потолок, а выводимый текст нейтрализуется для терминала и
  таблиц.
- **Готово к деплою**: Docker-образ без root, CronJob в Kubernetes, таймер systemd,
  `justfile`, CI в GitHub Actions.
- **Автодополнение оболочки** для bash, zsh, fish, elvish и PowerShell.

## Как это работает

1. **Выборка по JQL** — задачи отбираются запросом JQL и читаются страницами.
2. **Поток** — страницы уходят в ограниченный канал, задачи обрабатываются конкурентно по
   мере поступления (backpressure — не более `concurrency × 2` задач в работе).
3. **Извлечение текста** — по задаче текст берётся из полей, из всех страниц ветки
   комментариев и, при `--scan-attachments`, из тел текстовых вложений; вложенный JSON и
   Atlassian Document Format обходятся рекурсивно, каждый сегмент обрезается по
   `max_text_size_kb`.
4. **Детекция** — по каждому сегменту проходят регулярные правила и детектор пар.
5. **Фильтрация** — allowlist, заглушки, энтропия, классы символов и контекстные слова
   отсекают вероятные ложные срабатывания; каждый отказ пишется в debug-лог с причиной.
6. **Маскирование и дедупликация** — совпадения сводятся к превью плюс хеш, сниппеты
   маскируются, находки дедуплицируются по (хеш секрета, rule_id).
7. **Сверка** — находки сверяются с постоянным хранилищем.
8. **Вывод** — отчёты, метрики и алерты; при `--incremental` запрос был сужен до окна с
   прошлого успешного скана, а после успешного скана пишется чекпоинт.

Карта модулей и внутреннее устройство — в [`ARCHITECTURE.md`](ARCHITECTURE.md).

## Установка

**Из исходников** (нужен Rust ≥ 1.97):

```bash
git clone https://github.com/wsgoggway/Jiraleaks
cd Jiraleaks
cargo build --release --locked
# бинарник: target/release/jiraleaks
```

**Docker**:

```bash
docker build -t jiraleaks .
```

## Быстрый старт

```bash
jiraleaks \
  --jira-url https://jira.example.com \
  --auth bearer \
  --jql "project = SEC AND updated >= -7d"
```

Токен берётся из первого непустого источника: `--pat`, затем `JIRA_PAT`, затем
`JIRA_API_TOKEN`. Пустая переменная не перекрывает реальный токен из источника с меньшим
приоритетом. Флаг `--dry-run` прогоняет весь конвейер, не записывая отчёты.

## Аутентификация

| Режим | Где применять | Учётные данные |
| --- | --- | --- |
| `bearer` (по умолчанию) | Jira Server / Data Center, PAT | `--pat`, иначе `JIRA_PAT`, иначе `JIRA_API_TOKEN` |
| `basic` | Jira Cloud (email + API-токен) | `--email` / `JIRA_EMAIL` + токен выше |
| `none` | Публичные инстансы без аутентификации | нет |

### `--incremental`

**Работает, по умолчанию выключен.** С `--incremental` запрос, уходящий в Jira, сужается до
задач, изменившихся после прошлого успешного скана того же запроса:

```text
(<настроенный JQL>) AND updated >= "<yyyy-MM-dd HH:mm>"
```

Чекпоинт — файл `checkpoint.json` в `--state-dir`. Он версионирован и хранит момент
завершения прошлого скана, **настроенный** JQL, базовый URL Jira и статус скана.

- Сужение применяется только если чекпоинту можно доверять: файл существует и разбирается,
  версия формата актуальна, статус — `success`, JQL совпадает с настроенным (сравнение со
  схлопнутыми пробелами, поэтому переформатированный запрос остаётся тем же самым),
  `jira_url` указывает на этот же инстанс, а время — корректный момент RFC 3339 в прошлом.
  В любом другом случае выполняется полный скан, а причина пишется в лог на уровне `info` —
  молчаливого сужения не бывает.
- Окно начинается на **5 минут** раньше этого момента, чтобы задача, обновлённая во время
  прошлого скана, попала в следующий запрос, а не выпала из всех последующих окон.
- Настроенный JQL всегда заключается в скобки перед добавлением `AND`: без скобок `OR` в
  запросе связал бы `AND` только с последним операндом, и половина запроса осталась бы без
  фильтра.
- Чекпоинт пишется только когда `--incremental` включён **и** скан завершился успешно;
  отменённый или частично упавший скан не сдвигает базу, иначе необработанные задачи
  выпали бы из всех последующих окон.
- В отчётах указан запрос, который реально выполнялся (`scan_run.jql`); чекпоинт хранит
  настроенный запрос как базу для следующего запуска.

**Про часовой пояс.** Метка времени записывается как наивное UTC (`yyyy-MM-dd HH:mm`), а Jira
трактует наивную метку в JQL в часовом поясе профиля пользователя, от имени которого идёт
запрос. На инстансе, чей профиль не в UTC, окно сдвигается на эту разницу; перекрытие в
5 минут компенсирует расхождение часов, а не разницу часовых поясов, поэтому для такого
инстанса перекрытие нужно увеличить.

Без флага ничего инкрементального не происходит: только `--incremental` читает и пишет
чекпоинт.

### Валидация

`Config::validate()` выполняется до первого запроса в Jira и отвергает (код выхода `1`):
пустой `jira_url` или URL без схемы, пустой JQL, отсутствие токена при `auth != none`,
`basic` без email, неизвестный `auth`, нулевые `page_size`, `concurrency`,
`max_findings_per_issue`, `max_text_size_kb` или `max_attachment_size_mb`, неизвестный
`report_layout`, неизвестный `min_confidence` и неизвестный формат отчёта. Командная
строка, которую отверг сам clap, завершается тем же кодом `1`.

> `github_token_checksum`; неизвестное имя валидатора принимает любое значение.

## Детектор пар «логин-пароль»

Отдельный детектор (`rule_id: credential_pair`, severity **High**) ищет пары
логин/пароль, оказавшиеся рядом:

- **userinfo в URL** — `scheme://user:pass@host`.
- **Близость ключ-значение** — ключ вида логина и ключ вида пароля на расстоянии не более
  200 байт друг от друга, построчно (`user`/`username`/`login`/`email`/`client_id`/… против
  `pass`/`password`/`passwd`/`pwd`/`secret`/`api_key`/…).
- **JSON-объекты** — соседние поля логина и пароля; дубликаты по алиасам схлопываются, так
  что один секрет даёт одну находку.

Находки пар всегда отдаются с высокой уверенностью, пароль заменяется маскированным превью
и хешем.

Стоимость детектора ограничена, потому что текст враждебен по определению: проверяется не
более **64 КиБ сегмента**, материализуется не более **4096 совпадений на шаблон**, и на
сегмент возвращается не более **256 находок**. Эвристика близости сравнивает совпадения
двумя монотонными курсорами, а не декартовым произведением, поэтому сегмент из
полумиллиона повторов `user=a\npassword=b\n` обрабатывается за миллисекунды, а не за минуты.

## Свои правила

Дополнительные или перекрывающие правила задаются файлом `--rules path/to/rules.yaml`.
Пользовательское правило перекрывает встроенное с тем же `rule_id`. Поддерживаются поля:

`rule_id`, `description`, `severity`, `confidence`, `regex` (fancy-regex),
`capture_group`, `min_length`, `min_entropy`, `context_keywords`, `denylist`, `validator`,
`enabled`, `ignore_if_contains`, `min_digits`, `min_uppercase`, `min_lowercase`,
`min_special_chars`, `special_chars`, `disable_default_placeholders`, `examples`,
`references`.

```yaml
- rule_id: my_custom_token
  description: Internal service token
  severity: high
  confidence: high
  regex: '\bsvc_[A-Za-z0-9]{32}\b'
  min_entropy: 3.0
  min_digits: 1
  context_keywords:
    - service_token
    - svc-token
  references:
    - https://wiki.example.com/auth/tokens
```

## Подавление ложных срабатываний

- **Allowlist** (YAML) — подавление по значению, SHA-256, регулярному выражению, `rule_id`,
  ключу задачи, ключу проекта и пути поля. См. следующий раздел.
- **Общий словарь заглушек** — 18 слов в одной таблице, читаемой в двух режимах:
  - список по умолчанию для `ignore_if_contains` движка правил — **подстрока**
    (14 слов: `example`, `test`, `sample`, `demo`, `dummy`, `placeholder`, `changeme`,
    `your_key`, `yourkey`, `your-key`, `xxxx`, `foobar`, `redacted`, `fake`); совпадение,
    содержащее любое из них, отбрасывается, а правило может отказаться от списка через
    `disable_default_placeholders: true`;
  - детектор пар и постобработка используют режим **равенства** (10 слов — те же шесть
    плюс `password`, `secret`, `your_secret_here`, `xxxxxx`) и маркеры шаблонов
    (`<...>`, `${...}`, `{{...}}`). Поэтому `xxxx` — заглушка для совпадения с правилом, но
    допустимый пароль для детектора пар.
- **Энтропия, классы символов, контекстные слова и denylist** — фильтры уровня правила.
- **Потолок находок на задачу** (`--max-findings-per-issue`).
- Каждый отброшенный кандидат пишется в debug-лог с правилом, задачей, путём поля и
  причиной — но без значения.

## Allowlist

Allowlist — список записей в YAML. Предикаты внутри записи объединяются по ИЛИ, записи по
файлу — тоже по ИЛИ:

```yaml
- value: "AKIAIOSFODNN7EXAMPLE"        # точное значение секрета, где угодно
  reason: "публичный пример из документации AWS"
- sha256: "9f86d081884c7d659a2feaa0c55ad015a3bf4f1b2b0b822cd15d6c15b0f00a08"
- pattern: '^ghp_example_'             # regex ищется внутри значения
  field: comment                       # ... только в поддереве комментария
  reason: "фрагменты документации"
- rule_id: aws_access_key_id           # целое правило
  project_key: SEC                     # ... только в одном проекте
- issue_key: SEC-123                   # одна задача
```

- `value` сравнивается побайтово; `sha256` принимает 64 hex-цифры с префиксом `sha256:`
  или без него, без учёта регистра; `pattern` ищется в значении как `fancy_regex` и
  ограничен бюджетом бэктрекинга (превысивший бюджет шаблон логируется и считается **не**
  совпавшим, то есть находка сохраняется).
- `rule_id`, `issue_key` и `project_key` сравниваются точно и с учётом регистра;
  `project_key` — часть ключа задачи до первого `-`.
- `field` — это **скоуп**, а не предикат: он сужает запись целиком, включая ключевые
  предикаты, до пути поля находки или его подпути. `field: comment` покрывает `comment`,
  `comment.body` и `comment.comments[0].body`, но не `comments`, не `commentary` и не
  `fields.comment`.
- `reason` нужен только для аудита: на сопоставление не влияет и пишется в debug-лог вместе
  с подавлением, которое объясняет. Значение секрета не логируется никогда.

Загрузка строгая, потому что молча бесполезная запись — это пропущенная утечка: неизвестный
ключ, запись без предиката (`field` сам по себе предикатом не является), пустые
`value`/`pattern`/`sha256`, битый дайджест или некомпилируемое регулярное выражение — это
ошибка конфигурации (код выхода `1`) с указанием проблемной записи. Пустой файл allowlist
корректен, ничего не подавляет и логируется как предупреждение.

## Комментарии и вложения

### Комментарии

При `--comments-mode all` (по умолчанию) сканируются **все** комментарии задачи, а не только
первая страница, встроенная в тело задачи. Остальные страницы читаются из эндпоинта
комментариев, не более 40 страниц по 50 комментариев (2000 комментариев после первой
страницы); при достижении потолка пишется предупреждение, скан продолжается. Ошибка
выгрузки логируется и никогда не роняет задачу: остальные находки по ней отдаются.
`--comments-mode none` читает только то, что уже есть в теле задачи.

### Вложения

`--scan-attachments` по умолчанию выключен. Когда он включён, вложение скачивается и
сканируется только если оно может быть текстом:

- **Сканируемые расширения** (`TEXT_EXTENSIONS`): `txt`, `log`, `env`, `ini`, `conf`, `cfg`,
  `properties`, `pem`, `key`, `crt`, `cer`, `pub`, `json`, `yaml`, `yml`, `toml`, `xml`,
  `csv`, `sql`, `md`, `sh`, `ps1`, `py`, `rb`, `js`, `ts`, `go`, `rs`, `java`, `tf`,
  `tfvars`, `dockerfile`, `gitconfig`, `npmrc`.
- **Файлы без расширения**, распознаваемые по полному имени: `Dockerfile`, `Makefile`,
  `Gemfile`.
- **Текстовые MIME-типы** принимают вложение с неизвестным расширением: `text/*`,
  `application/json`, `application/xml`, `application/x-yaml` (параметры вроде
  `; charset=utf-8` игнорируются).
- **Никогда не скачиваются**: архивы и сжатые файлы (`zip`, `tar`, `gz`, `tgz`, `bz2`,
  `xz`, `7z`, `rar`), исполняемые файлы и библиотеки (`exe`, `dll`, `so`, `dylib`, `bin`,
  `iso`), изображения (`png`, `jpg`, `jpeg`, `gif`, `bmp`, `ico`, `webp`, `svg`), PDF и
  офисные форматы (`doc(x)`, `xls(x)`, `ppt(x)`, `odt`, `ods`, `odp`). Denylist
  проверяется **до** allowlist, поэтому вводящий в заблуждение MIME-тип не заставит
  скачать архив. Архивы пропускаются потому, что лимит размера считается по пришедшим
  байтам: 1 МБ `.zip` проходит любой лимит на файл и может развернуться в гигабайты, а
  текст внутри архива всё равно потребовал бы отдельного ридера. Бинарные и офисные
  форматы пропускаются потому, что потерянное UTF-8-декодирование сжатых или структурных
  данных даёт шум, а не проверяемые находки.

Ограничения помимо `--max-attachment-size-mb` (на файл, по умолчанию 10 МБ):

- **20 вложений на задачу** — потолок по числу запросов, а не по байтам.
- **32 МиБ на задачу** суммарно по всем вложениям — именно это ограничивает память
  сканера значением `concurrency × 32 МиБ` при дефолтах: один лимит на файл допускал бы
  20 × 10 МБ на задачу.

Заявленный размер проверяется до запроса, поэтому слишком большой файл не стоит ничего, и
тот же лимит применяется повторно при потоковом чтении: тело читается порциями и
обрезается на лимите, поэтому ответ без `Content-Length`, с ложной длиной или со
сжатием gzip не сможет выделить память сверх лимита.

URL вложения (`content`), который сообщает Jira, контролируется автором вложения, поэтому он
обязан указывать на **тот же origin**, что и базовый URL Jira: та же схема, хост и
эффективный порт. Чужой хост, понижение схемы, другой порт, протокол-относительный
`//host/path`, `file:` или `javascript:` отвергаются с предупреждением и не скачиваются (это
защита от SSRF, и это сравнение origin, а не префикса, поэтому
`https://jira.example.com.evil.tld/…` не проходит). URL проверяется повторно внутри вызова
скачивания, так что проверку нельзя обойти со стороны вызывающего кода.

Скачанное вложение становится сегментом `attachment[<имя файла>]`: имя очищается от
терминальных escape-последовательностей, схлопывается по переводам строк и табуляции и
обрезается до 128 символов, потому что оно повторяется в каждой находке этого вложения и в
каждом отчёте. Во всём остальном скан не меняется — текст вложения проходит тот же движок
правил, детектор пар, allowlist и цепочку уверенности, что и описание. Вложение, которое не
удалось скачать, декодировать или которому нельзя доверять, логируется и попадает в
счётчики; задачу оно не роняет.

Сводка сообщает реальные счётчики `comments_scanned` и `attachments_scanned` — количество
просканированных тел комментариев и текстов вложений.

## Отчёты

| Формат | Расширение файла | Описание |
| --- | --- | --- |
| `json` | `.json` | Один JSON-документ со сведениями о скане и всеми находками (по умолчанию). |
| `ndjson` | `.ndjson` | По одному JSON-объекту на строку. |
| `csv` | `.csv` | Таблица находок. |
| `sarif` | `.sarif` | SARIF 2.1.0 для интеграции с IDE и CI. |
| `summary` | `.txt` | Человекочитаемая сводка. |
| `defectdojo` | `.defectdojo.json` | DefectDojo Generic Findings Import JSON. |

- `--format` — список через запятую. `all` может стоять в любом месте списка (`json,all`
  ведёт себя как `all`), дубликаты схлопываются, а неизвестное или пустое имя — ошибка
  (код выхода `1`), возникающая до создания каталогов: молчаливого «ничего не записалось»
  не бывает.
- `--report-layout flat` (по умолчанию) пишет
  `<report-dir>/<дата>T<время>_report.<ext>`. `nested` пишет
  `<report-dir>/<проект>/<дата>/<время>_report.<ext>`, где `<проект>` — один токен проекта
  из JQL (`project = SEC` и `project in (SEC)` дают `SEC`; несколько проектов — `_multi`;
  всё остальное — `_default`). Сегмент фильтруется до `[A-Za-z0-9_-]` и повторно проверяется
  как обычный компонент пути, поэтому враждебный JQL не может записать отчёт вне
  `--report-dir`.
- **Сниппеты всегда маскированы.** Сниппет — окно ±50 байт вокруг совпадения, поэтому в нём
  могут оказаться секреты соседних находок того же сегмента; каждый из них заменяется на
  `[REDACTED:<rule_id>]` до того, как сниппет попадёт в отчёт, хранилище находок или алерт.
  Маскированный секрет — превью из первых двух и последних двух символов (`[REDACTED]` для
  значений короче 8 символов) плюс хеш `sha256:`.
- **CSV**: из ячеек удаляются управляющие символы, а если первый видимый символ — сигнал
  формулы таблицы (`=`, `+`, `-`, `@`), ячейка получает апостроф в начало. Так сниппет не
  выполнится при открытии отчёта в Excel или LibreOffice.
- **Сводка** очищается от терминальных escape-последовательностей (CSI, OSC — включая
  запись в буфер обмена OSC 52 — и прочих управляющих символов).

### SARIF

Результаты несут URL задачи Jira, ключ задачи, путь поля, уверенность, статус, хеш секрета
и теги. `tool.driver.rules` заполняется для каждого правила, на которое ссылаются
результаты: описание строится по самим находкам, а `defaultConfiguration.level` получает
самый серьёзный уровень, который это правило дало.

Незавершённый скан говорит об этом прямо: `invocations[].executionSuccessful` равно `false`
для частичного или упавшего скана, и рядом добавляется `toolExecutionNotifications` с
покрытием (`N of M issues scanned, E errors`) — частичный скан нельзя читать как
доказательство отсутствия утечек.

### DefectDojo

Формат Generic Findings Import JSON, импортируется с `scan_type=Generic Findings Import`.

- `unique_id_from_tool` — это `fp:<64 hex>#<ordinal>`, детерминированный отпечаток основной
  локации находки `(secret_hash, rule_id, issue_key)`. Он одинаков при каждом скане одного
  и того же состояния, поэтому DefectDojo обновляет существующую запись, а не создаёт
  новую, и закрывает находку, которая перестала находиться. (Раньше сюда уходил UUID,
  который пересоздавался каждый скан, и каждый импорт создавал новые находки.)
- `verified` равно `true` только когда внешняя валидация подтвердила, что учётные данные
  живые: совпадение с правилом — кандидат, а не подтверждение, и импорт кандидатов как
  verified скрывает работу по триажу.
- `active` и `false_p` взаимоисключающие: Closed, Resolved и FalsePositive импортируются
  неактивными, ложное срабатывание — тоже неактивным, чтобы находка, которую скан сам
  отклонил, не открывалась заново.

## Хранилище находок

Когда задан URL базы (`--db-url`, по умолчанию `sqlite://{state_dir}/findings.db`), находки
сохраняются и сверяются между сканами:

- **Статусы**: `new`, `recurring`, `closed`, `confirmed`, `false_positive`, `resolved`.
- Идентичность — детерминированный отпечаток по `(secret_hash, rule_id, issue_key)`,
  поэтому секрет, найденный в N задачах, даёт N строк со своей историей. Находка, которой
  нет в пересканированной задаче, помечается `closed`; повтор становится `recurring` с
  сохранённым `first_seen` и увеличенным `times_seen`. Задачи, не попавшие в текущий JQL,
  не трогаются и никогда не закрываются ложно.
- Поддерживается и PostgreSQL (`postgres://user:pass@host/db`).
- Внешняя система валидации может наполнять таблицу `live_validations` (по хешу секрета);
  подтверждённые секреты отражаются в находках и могут повышать severity. **Провайдер
  внешней валидации в сам jiraleaks не встроен** — таблица представляет собой слот схемы
  для внешнего чекера.

## Алерты

Уведомления настраиваются файлом `--alerts path/to/alerts.yaml`:

```yaml
slack:   { webhook_url: "https://hooks.slack.com/services/..." }
teams:   { webhook_url: "https://outlook.office.com/webhook/..." }
webhook: { url: "https://example.com/hook" }
min_confidence: medium
```

Каждый канал отправляет сводку скана и лучшие находки, отфильтрованные по
`min_confidence` (по умолчанию `medium`): Slack и Teams — 10 находок с наибольшей
уверенностью в виде строк со ссылками, произвольный вебхук — до 20 находок вместе со
сведениями о скане.

Конфигурация проверяется строго, до скана: неизвестный ключ, нечитаемый файл, конфиг без
единого канала, пустой URL канала и неверный `min_confidence` — всё это ошибки
конфигурации (код выхода `1`). Иначе опечатка в `webhook_url` молча отключала бы канал, а
опечатка в `min_confidence` раньше откатывалась к `low` и отправляла находки с низкой
уверенностью в рабочий канал.

Все три канала используют один HTTP-транспорт с таймаутом 10 секунд и доставляются
параллельно, поэтому недоступный адресат стоит одного таймаута, а не одного на канал.
Доставка по контракту fire-and-forget — упавший вебхук не роняет скан, — но итог
логируется точными счётчиками delivered/failed, а упавший канал учитывается как его
собственная ошибка и не лишает соседние каналы доставки. URL вебхуков — это bearer-секреты,
они не логируются и не печатаются в `Debug`.

## Метрики

`--metrics-path <PATH>` пишет сводку скана (задачи, находки по severity, ошибки,
длительность, версия сканера). `--metrics-format` принимает `json` (по умолчанию), `prom` и
`prometheus`; устаревшее написание `text` отвергается. Каталог назначения создаётся, если
его нет.

## Развёртывание

- **Docker** — многоступенчатая сборка, запуск без root под UID/GID 65532, `WORKDIR /data`.
  Образ задаёт `REPORT_OUTPUT_PATH=/data/reports` и
  `JIRALEAKS_DB_URL=sqlite:///data/state/findings.db?mode=rwc` и объявляет тома
  `/data/reports` и `/data/state`. У `--state-dir` нет переменной окружения: чтобы чекпоинты
  легли на том, передайте `--state-dir /data/state`. Сборка — `docker build -t jiraleaks .`,
  запуск — с переменными `JIRA_*`; `docker run --rm jiraleaks --help` не требует учётных
  данных.
- **CronJob в Kubernetes** — см. [`deploy/k8s/cronjob.yaml`](deploy/k8s/cronjob.yaml):
  еженедельно (понедельник, 03:00 UTC), пространство имён `security`, политика
  `Forbid`, PVC общий для отчётов и хранилища находок и `securityContext` под UID 65532
  (`runAsNonRoot`, `readOnlyRootFilesystem`, сброшенные capabilities). Учётные данные берутся
  из Secret `jira-credentials`.
- **Таймер systemd** — см. [`deploy/systemd/`](deploy/systemd/): недельный
  `jiraleaks.timer` запускает oneshot-сервис `jiraleaks.service`, учётные данные лежат в
  `/etc/jiraleaks/env` (права 0600), используется `StateDirectory=jiraleaks` и
  ужесточённый профиль юнита.
- **Task-runner** — `just --list` показывает рецепты: `build`, `test`, `lint`, `lint-strict`,
  `fmt`, `fmt-check`, `docker-build`, `docker-smoke`, `docs-mermaid`, `scan`, `clean`.
- **CI** — [`.github/workflows/ci.yml`](.github/workflows/ci.yml) выполняет
  `rustfmt --check`, `clippy`, `cargo test --all-targets` и сборку Docker-образа с
  smoke-проверкой точки входа.

В примерах используется общий JQL `project = SEC`; подставьте своё окружение.

## Коды выхода

| Код | Значение |
| --- | --- |
| `0` | Успех — включая скан, завершившийся с некритичными ошибками по отдельным задачам. |
| `1` | Ошибка конфигурации: неверные значения, непригодный файл allowlist или алертов, отклонённая clap командная строка. |
| `2` | Ошибка доступа к Jira (неудачная аутентификация, недоступный хост, отвергнутый origin вложения). |
| `3` | Критическая ошибка скана или неклассифицированная внутренняя ошибка — сбой, помешавший выполнить этап. |
| `4` | Ошибка записи отчёта (тот же код у ошибок записи чекпоинта и каталога состояния). |
| `5` | Ошибка хранилища. |

## Безопасность

- jiraleaks работает с Jira **только на чтение**: забирает задачи, комментарии и (по флагу)
  тела вложений и никогда не меняет состояние Jira.
- **Сырые секреты не попадают ни в один приёмник.** В отчётах, хранилище находок, логах и
  алертах только маскированный превью (первые два и последние два символа) и хеш SHA-256.
  Сниппет маскируется как для самого совпадения, **так и для всех остальных секретов,
  найденных в том же окне**, поэтому соседняя находка не может через него утечь. Реализации
  `Debug` у конфигурации, сырого совпадения и кандидата печатают токен и секрет как `***`
  или превью.
- **Логи маскируются**: токен, URL вебхуков алертов и найденные секреты не появляются в
  сообщениях лога, а `Debug` у `Config` маскирует `pat`.
- **Текст из Jira — недоверенный ввод.** Сводка удаляет терминальные escape-последовательности
  (включая запись в буфер обмена OSC 52) и управляющие символы; CSV нейтрализует формулы
  таблиц; имена вложений очищаются и обрезаются по длине, прежде чем стать путями полей;
  весь выводимый текст проходит через один санитайзер.
- **Вложения скачиваются только с настроенного origin Jira** — защита от SSRF сравнивает
  схему, хост и эффективный порт, а не префикс URL, а загрузка идёт потоком под лимитом на
  файл и бюджетом байт на задачу.
- **Потолки стоимости на враждебном вводе**: детектор пар читает не более 64 КиБ сегмента и
  возвращает не более 256 находок, пагинация комментариев ограничена, число и объём вложений
  на задачу ограничены, а `--max-findings-per-issue` ограничивает вывод по одной задаче.
- **Конфигурация проверяется строго**: CLI, allowlist и конфиг алертов отвергают неизвестные
  ключи и непригодные значения при старте, а не деградируют молча.
- Используйте для сканирования **аккаунт Jira с минимальными правами и только на чтение** и
  держите `.env`, отчёты и хранилище находок вне системы контроля версий (`.gitignore` и
  `.dockerignore` репозитория уже покрывают `reports/`, каталоги состояния и `*.db`).
