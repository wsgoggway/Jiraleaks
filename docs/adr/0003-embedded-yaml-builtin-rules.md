# 0003. Встроенный YAML-корпус правил с переопределением по `rule_id`

- Статус: принято
- Дата: 2026-09-24

## Контекст

Сканер должен находить типовые секреты сразу после установки: ключи AWS, токены GitHub,
GitLab, Slack, Telegram, Stripe, npm, SendGrid, Google, приватные ключи, JWT, строки
подключения с паролем и обобщённые присваивания паролей, ключей и секретов. При этом
корпоративные особенности — внутренние форматы токенов, шумные для конкретной инсталляции
правила — должны настраиваться без форка и без пересборки.

## Решение

20 встроенных правил лежат в бинарнике как встроенный YAML
(`detectors/builtin.rs::BUILTIN_RULES_YAML`) и загружаются всегда. Пользовательский файл
(`--rules`, `RULES_PATH`) читается поверх: правила складываются в карту по `rule_id`, и
запись пользователя заменяет встроенную с тем же идентификатором. Итоговый набор
компилируется один раз при старте (`RulesEngine::new`), отключение правила — `enabled: false`
в пользовательской записи.

## Альтернативы

- **Только внешние правила (файл рядом с бинарником).** «Сканировать без настройки» перестало
  бы работать, а файл пришлось бы распространять, версионировать и обновлять отдельно от
  бинарника — классический источник расхождения «какая версия правил на этом хосте».
- **Каталог правил на диске (rulepack).** Даёт независимые обновления корпуса, но требует
  упаковки, подписи и управления версиями — избыточно для утилиты, которая сознательно
  ставится как один файл.
- **Правила в коде (структуры Rust).** Компилятор проверяет их, но изменить критичность,
  добавить `denylist` или выключить шумное правило без пересборки уже нельзя, а именно это
  и требуется эксплуатации.
- **Оверлей только «добавить новое».** Не покрывает главный сценарий: правило с шумной
  регуляркой нужно *заменить* или выключить, а не дополнить.
- **Полное слияние полей правила.** Позволяло бы дописать `context_keywords` к встроенному
  правилу, но делает результат неочевидным: непонятно, какое правило реально работает.
  Выбрана замена целиком, при которой конфигурация читается однозначно.

## Последствия

- Работает без настройки; версия корпуса правил совпадает с версией сканера и видна в отчётах
  как `scanner_version`.
- Переопределение по `rule_id` покрывает все задачи эксплуатации: сменить регулярку,
  критичность, добавить `denylist`, выключить правило. Чтобы «дополнить» встроенное правило,
  его копируют в пользовательский файл и правят копию — цена явности.
- Правки корпуса требуют новой версии бинарника; для экстренного исключения шумного
  срабатывания есть allowlist, который работает без пересборки (см. `docs/adr/` и
  `src/allowlist.rs`).
- Поле `examples` каждого правила прогоняется тестом против его же регулярки, поэтому
  опечатка в встроенном правиле не проходит CI.
- Регулярки компилируются на старте: несобирающаяся регулярка в пользовательском файле —
  ошибка конфигурации, а не молчаливо пропущенное правило.
